# Event Schema

All events in the Ainsel platform use a simplified pass-through format: the
connector wraps the raw webhook body and HTTP headers into an `Event` struct
and POSTs it to the hub without normalization. The [`shared/api`](../shared/api/)
Go module defines the `Event` struct.

## Event Structure

```json
{
  "id": "evt-forgejo-1718934000000123456",
  "version": "1",
  "connector": "forgejo",
  "timestamp": "2026-04-24T10:30:00Z",
  "headers": {
    "X-Forgejo-Event": "issues",
    "X-GitHub-Event": "issues",
    "content-type": "application/json"
  },
  "data": { ... },
  "raw": "..."
}
```

### Top-Level Fields

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique event identifier (generated by the connector) |
| `version` | string | Schema version (currently `"1"`) |
| `connector` | string | Connector instance name (e.g. `forgejo`) |
| `timestamp` | ISO 8601 | When the connector received the webhook |
| `headers` | map[string]string | HTTP headers from the webhook delivery |
| `data` | json.RawMessage | Raw webhook body as parsed JSON |
| `raw` | string | Original raw webhook body as a string |

### Design Rationale

The `Event` struct is intentionally minimal. It does **not** include
`source`, `type`, `subject`, `actor`, or `action` as top-level fields.
Instead, all source-specific information is carried by the raw `data`
payload and the `headers` map. This design was chosen to reduce connector
complexity — connectors simply wrap the webhook delivery without needing
to understand or normalize the source's payload format.

The previous canonical schema (with `type`, `subject`, `actor`, `action`
fields) was superseded.

## NATS Subject

Events are published to the NATS subject `events.<connector>`. The event
type is **not** part of the subject — all events from a connector go to
the same subject.

| Subject | Example |
|---------|---------|
| `events.<connector>` | `events.forgejo` |

The hub subscribes to `events.*` (all connector subjects) and performs
trigger matching in-process.

## Trigger Matching

The hub's trigger index builds a filter payload from each event by merging
the `data` (raw JSON body) and `headers` into a single flat map:

- **Body fields** are available at the top level (e.g. `action`, `issue.number`).
- **Headers** are nested under the `headers` key (e.g. `headers.X-Forgejo-Event`).
- A synthetic `type` key is derived from well-known webhook event-type headers
  (`X-Forgejo-Event`, `X-Gitea-Event`, `X-Github-Event`) so triggers can match
  on event type with a filter like `{field: "type", op: "eq", value: "issues"}`.

### Example Filter Payload

For a Forgejo `issues` webhook with body `{"action": "opened", "issue": {"number": 42, ...}}`:

```json
{
  "action": "opened",
  "issue": {
    "number": 42,
    "title": "Login page throws 500 error",
    ...
  },
  "headers": {
    "X-Forgejo-Event": "issues",
    "content-type": "application/json"
  },
  "type": "issues"
}
```

### Filter Examples

| Filter | Description |
|--------|-------------|
| `{field: "type", op: "eq", value: "issues"}` | Match Forgejo issue events |
| `{field: "action", op: "eq", value: "opened"}` | Match "opened" action in the webhook body |
| `{field: "issue.title", op: "contains", value: "bug"}` | Match issues with "bug" in the title |
| `{field: "headers.X-Forgejo-Event", op: "eq", value: "push"}` | Match Forgejo push events by header |

## Connector Headers

Connectors pass through the HTTP headers from the webhook delivery. The
following well-known headers are used by the platform:

| Header | Source | Purpose |
|--------|--------|---------|
| `X-Forgejo-Event` | Forgejo | Event type (e.g. `issues`, `pull_request`, `push`) |
| `X-Gitea-Event` | Gitea | Event type (same format as Forgejo) |
| `X-Github-Event` | GitHub | Event type (e.g. `issues`, `pull_request`, `push`) |
| `content-type` | All | MIME type of the webhook body |

The hub's trigger index checks these headers in order
(`X-Forgejo-Event` → `X-Gitea-Event` → `X-Github-Event`) to derive the
synthetic `type` field for filter matching. If none of these headers are
present, it falls back to a generic `type` header if set by the connector.

## Hub Routing Headers

When the hub routes an event to an agent, it copies the original event
headers into the task and adds routing metadata. The agent runner receives
these headers via the `next-task` API response.

| Header | Set By | Purpose |
|--------|--------|--------|
| `type` | Router / Cron / Chat | Canonical event type, derived platform-independently (e.g. `"issues"`, `"push"`, `"cron"`, `"chat.message"`) |
| `X-Trigger-Name` | Router / Cron / Chat | Name of the trigger that matched the event (e.g. `develop-on-assign`) |
| `X-Invocation-ID` | Router / Cron | Unique invocation ID for tracking and completion reporting |

For webhook events the router derives the `type` value from any HTTP
header ending in `-Event` (e.g. `X-Forgejo-Event`, `X-Gitea-Event`,
`X-Github-Event`, `X-GitLab-Event`) so the system works with any webhook
source without hardcoding provider-specific header names. For cron and
chat events the hub sets `type` directly (`"cron"`, `"chat.message"`).

The original webhook headers are passed through alongside these routing
headers for informational purposes.

### Event Type Derivation in the Runner

The agent runner reads the canonical `type` header set by the hub and
combines it with the `action` field from the webhook payload to produce
a compound event type:

| `type` header | `action` from payload | Resulting event type |
|---------------|----------------------|---------------------|
| `issues` | `opened` | `issues.opened` |
| `pull_request` | `assigned` | `pull_request.assigned` |
| `push` | *(none)* | `push` |
| `cron` | *(none)* | `cron` |
| `chat.message` | *(none)* | `chat.message` |

The runner does **not** inspect provider-specific headers
(`X-Forgejo-Event`, etc.) — all platform normalization happens in the hub.

## Agent API Authentication

Internal service-to-hub communication (agent runners, webhook receivers,
MCP servers) is authenticated with a shared-secret header:

| Header | Purpose |
|--------|--------|
| `X-Internal-Token` | Shared secret for internal API calls (task polling, ack/nack, task logs, event ingestion) |

The hub validates this header on all `/api/v1/agents/:name/*` and
`/api/internal/*` endpoints. The token is provisioned per-agent by the
operator and set as the `AGENT_TOKEN` environment variable in the agent pod.

## Chat Events

Chat events are created by the hub when a user sends a message via the
chat API. They bypass the trigger matching engine — the hub enqueues them
directly as a task for the target agent with the header `type` set to
`"chat.message"`. The agent responds via the `mcp__chat__send_reply` MCP
tool, not by posting a Forgejo comment.

The task `data` payload contains `session_id` and `message` fields.
